# Toolkit bulk downloads (v4.33)

## Remembered mapping and selections (v4.33)

Import the metadata CSV once. Its text, source filename, import timestamp and exact folder-selection rules are saved in the browser's IndexedDB and restored on the next Manage Documents visit. The panel shows **Saved in this browser**, **Restored from this browser**, or an explicit save error. The source filename and import date stay visible. This is a cached snapshot, not a live link to the disk file; replacing or deleting that CSV on disk does not update the cached mapping. No mapping is embedded in the published userscript or uploaded by the Toolkit.

Import a fresh CSV to replace the saved mapping. A valid import starts with the usual ACS21 selection when present, so review selections again. Invalid imports block downloading for that session and preserve the previous valid browser record. Checkbox changes, exclusions, Select all and Clear all automatically save their rules; an empty selection stays empty across reloads. Writes are serialized. Saving failures leave the current mapping usable but explicitly report that it will not be remembered. Startup waits for storage reads before allowing downloads, and corrupt saved data blocks flat fallback until replaced or cleared.

**Clear saved mapping** removes the cached CSV and selection rules, clears the file input and returns to explicit flat-download mode. It does not remove your CSV backups, chosen download folder, speed preferences or downloaded files. If browser deletion fails, the panel warns that old data may return on reload. Clearing browser site data or switching browser profiles can lose this cache; the disk copies are your independent backup. The source files are backed up locally at `C:\Users\Phaderon\Documents\Resource Centre\Mapping`. No automatic disk-folder scanning or permission request is added.

Offline integration tests cover restore without a selected CSV, remembered exclusions and empty selections, replacement, invalid imports preserving the previous record, corrupt stored rules, blocked startup, save failures, clearing and subsequent reload. Live persistence still needs confirmation after one import and page refresh.

## Searchable multi-folder picker (v4.32)

Load the bulk metadata CSV, then click **Resource Centre folders** to browse its expandable tree. Tick a parent to include that folder and all descendants. Untick a branch to exclude it; you can tick a deeper descendant to include it again. Partly selected parents show a mixed checkbox. Reticking a parent selects its whole branch and clears earlier descendant exceptions.

Search matches folder names or full paths and shows matching branches with their ancestors. It only changes visibility, never the selection. **Select all** and **Clear all** apply to the entire mapping, including folders hidden by search. **Done** closes the picker; changes apply immediately. No folders selected blocks mapped downloads. Folder controls are disabled during a run. From v4.33, CSV data and selection rules are remembered locally; a fresh import starts with the ACS21 default when available.

Use **Scan / preview** before downloading to see file counts, folder-copy counts and exact relative destinations. Only the currently displayed eligible Manage Documents rows can download, even with Select all. A document assigned to both an excluded folder and an included folder still gets its copy in the included folder. Every excluded assignment is omitted.

One selected root retains its own folder name, preserving the existing ACS21 archive layout. Multiple roots omit their shared parent ancestry, retaining enough hierarchy to distinguish their paths. For example, `Top > A` and `Top > B` produce `A/...` and `B/...`; roots under different top-level trees retain those top-level names. Select all retains complete mapped paths. Changing the set of selected roots can change relative destinations, so review the preview and choose the appropriate local root before proceeding; resume checks apply to those exact paths, without moving existing files. Excluding descendants within the same selected root preserves its original layout.

Offline verification includes `download-folder-picker-check.cjs` for exclusions, re-inclusions, multiple roots, shared assignments and all/none, plus `download-check.cjs` for picker interaction, mixed checkboxes, search preserving exclusions and global select-all under search. Live visual/browser interaction still needs user confirmation.

## Resume, results and Windows recovery (v4.31)

The Manage Documents panel now has styled controls, a wider layout, wrapped log entries, **Failed / Successful / Skipped / Recovery staged / All** result views, **Copy errors**, **Copy full log**, JSONL export and **Check recovery status**. Progress counts processed jobs including skips and failures, separately from saved copies. Existing copies are checked in a preflight pass; only missing copies enter the paced network queue. The initial scan still reports all mapped records, not only pending files. Clipboard failure falls back to the browser copy command and finally offers log export.

Each successful final copy is recorded in `.wrc-download-manifest.json` under the selected local download root: document ID, relative path, size, completion status and timestamp. Updates are serialized across concurrent jobs. A copy is completed only after the write closes and its size is checked. A missing or zero-byte file is incomplete even if a manifest record exists. Existing non-empty files from older runs are skipped without redownloading; they are not checksum verified. If a recorded size differs from a non-empty on-disk file, the Toolkit reports an error and preserves that file for review. Original non-empty files are never deliberately overwritten.

Some Windows browser writes fail on long paths, including temporary swap-file names. On a `NotFoundError` during the final copy, the Toolkit writes the already downloaded data under a short name in `.wrc-recovery` plus a small JSON job describing its intended relative destination. This is shown as **Recovery staged**, not a successful final copy. The browser does not fetch that document a second time to stage it. A ready marker is written only after the run's workers have finished/cancelled.

The separate local `repair-staged-downloads.py` helper performs final placement using Windows extended paths. It has no network access and installs nothing. It confines jobs to the chosen download root, verifies staged sizes, preserves non-empty destinations, replaces empty placeholders, writes through a short temporary file, records the completed copy in the same manifest and writes `.wrc-recovery/recovery-results.json`. It retains staged data for recovery. Invalid jobs and size mismatches are reported without replacing the destination. No other archive is moved and no Windows settings are changed.

For the current Syllabus archive, `start-syllabus-recovery.cmd` starts the helper for **one hour** using the existing Python installation and `%USERPROFILE%\Downloads\CRC Archive\Syllabus` as the root. Run it before retrying and leave it running until **Check recovery status** reports the result. The browser must select that same **Syllabus parent folder**, since the Toolkit itself adds `Army Cadet Syllabus 21 (ACS21)`. The helper waits for ready batches, performs no download requests, and can process more than one batch while active. For a different root, use the helper's `--root` argument with that exact local root. It never watches a whole drive or user profile.

For manifest entries recovered natively, the next run asks the active helper to verify current disk existence and size through local request/response JSON files. The browser waits up to three seconds and blocks with a clear message if the helper is unavailable, rather than trusting a stale record. Start the helper again on future sessions if native long-path entries exist. **Check recovery status** reads the helper's report and adds recovered copies/errors to the results panel. No native helper is launched by the userscript itself.

Tests: `node download-resume-check.cjs` covers zero placeholders, missing/stale records, size mismatch preservation, concurrent manifest updates and staging without false completion; `python repair-staged-check.py` checks actual Windows long-path copies, zero replacement and confinement. Existing mapping, speed, Manage Documents and home-card checks remain required. Updated page styling, clipboard and staging still need a user-run live check. Keep the tab open while downloading; export the log before refreshing.

## Speed controls and logs (Manage Documents, v4.30)

**Concurrent downloads** sets the maximum number of active file jobs (1-8, default 1). **Gap between starts** sets a global interval between starting jobs (0-60 seconds, fractional values allowed, default 1 second). This gap applies across the whole queue, not separately to each worker. Each slot stays occupied through URL resolution, downloading and saving all folder copies. With concurrency 1, the next file starts after the current file finishes and the start gap has elapsed. Settings are remembered locally when browser storage permits.

Both settings remain editable during downloading. Increasing concurrency permits more jobs to start; decreasing it lets current jobs finish before starting any above the new cap. Changing the gap updates subsequent launches. An empty or invalid live setting halts the run and cancels active requests. There is no automatic concurrency ramp, retry or rate-limit probing. The site's permitted download rate is unknown; the controls cannot guarantee that a run will avoid a server-side restriction.

Live progress includes active jobs, completed files, copies saved, failures, files/minute and average downloaded MiB/s. Stop cancels all URL resolvers and storage fetches, prevents queued starts and further folder copies, and lets an in-progress disk write finish. Runs wait for every active job to finish or cancel before the controls are unlocked. Existing filename merging ensures concurrent workers cannot independently write the same planned file.

HTTP 401/403/429/503, an explicit session redirect, a storage network failure, or an unavailable APEX helper halt the entire run and cancel other requests. Three consecutive failed jobs without a successful completion also halt the run (including unexpected HTML, empty responses, timeouts, disk errors and other HTTP errors). Previously completed files are retained. No automatic retries occur. Inspect the log and resolve any server/session issue before restarting; existing copies will be skipped on the next run. Retry-After is recorded when exposed by the failing response, but does not trigger an automatic restart. Cancellation of peer jobs is logged separately from the triggering failure. A failure response alone does not identify the site's security rules.

**Export download log** saves a JSONL file containing timestamped run starts/finishes, speed changes, file starts, successful response status, saved copies, skips, completion sizes/durations, errors with phase and HTTP status, exposed Retry-After, cancellations and halt reason. Logs cover this page session, including previous runs; export before refreshing. They include document IDs, filenames and relative destinations. They do not include signed storage URLs, cookies or session tokens. The visible panel shows the current scan/run. The export is generated locally and nothing is uploaded by the logger. Unknown error messages have URLs and obvious credential assignments redacted.

These controls apply to Manage Documents only; home-card downloads retain their existing sequential controls. Offline checks: `node download-speed-check.cjs`, `node download-check.cjs`, `node download-mapping-check.cjs`, and `node download-cards-check.cjs`. Updated controls, concurrency and real server reactions still need user-run live verification.

## Download a mapped folder tree (v4.29)

On Manage Documents, show all desired rows and keep File Name, Download and # Folder Entries visible. Load the **bulk document metadata CSV** using **Optional folder mapping CSV**. This export must contain **Select** (document ID) and **Folder Path**. From v4.33, the CSV is cached locally in the browser and preloaded after refresh; it is never uploaded by the Toolkit. The Folders and Manage Documents CSVs are not needed by the browser.

Choose a Resource Centre folder from the selector. ACS21 is selected automatically when present. **Scan / preview** lists matched IDs, filenames and relative destinations, counts folder copies, and reports mapped IDs absent from eligible displayed rows. It never creates folders or fetches files. Missing IDs may be off-page, filtered out, or have zero Folder Entries. The download rescans the current report on each click.

Choose a local **download folder** as the destination root. For example, choosing `D:\Syllabus` with ACS21 selected saves files beneath `D:\Syllabus\Army Cadet Syllabus 21 (ACS21)\[08] Expedition\4 Star\Assessments`. The selected folder's name is retained; its ancestors are omitted. Every matching assignment inside the selected tree receives a copy. Assignments outside the chosen tree are excluded by document ID, even when their filenames match. Archived records are included if displayed and mapped; apply a Published status filter if you want only published documents.

Click **Download displayed files** after reviewing the scan. Files with the same case-insensitive filename are fetched once, using the first matching displayed ID, and their mapped target folders are combined. No content comparison is performed. Existing files are skipped per destination folder, without overwriting or suffixes; missing copies still download. Folder names unsafe on Windows stop the plan rather than silently renaming directories. Stop prevents further copies after an in-progress write finishes. If a copy fails, previously saved copies remain; rerunning skips those and retries missing copies. The log records each saved or skipped destination, and the final summary counts completed files and saved copies.

Without a metadata CSV, the existing flat download behavior remains. A selected invalid CSV blocks downloading until corrected or cleared, so it cannot accidentally download every row. Existing throttling, authentication, HTML, permission and timeout protections remain in effect. Run `node download-mapping-check.cjs`, `node download-check.cjs` and `node download-cards-check.cjs` for offline verification. Real folder writes and the updated page controls still require a small user-run live check.

## Flat download from Manage Documents

Two entry points share the same protocol: the Manage Documents batch panel (below) and, from v4.28, a **Download** tab on the Resource Centre home page for quick downloads from the document cards you can see. See "Quick download from home cards" at the end.

The existing Toolkit now also runs on Manage Documents. On that page it shows only bulk download controls. The upload/home view remains available on the Resource Centre home page. The separate Archivist is not required for this workflow.

1. Update the Toolkit in Violentmonkey or Tampermonkey, then reload Manage Documents.
2. Apply the site's filters. Set the report rows per page to include the batch you want. Keep File Name, Download and # Folder Entries columns visible. Rows with zero Folder Entries are skipped and listed in the results, based on the user's observed broken downloads for these records.
3. Click **Choose download folder** and select the exact local batch folder in Chrome or Edge. Approve the browser's folder-write prompt. The last folder handle is saved in this site's IndexedDB and restored on refresh; clicking Download may require renewed write permission. Choose download folder changes the remembered folder. Clearing site data removes this memory. It is separate from the uploader's remembered source folder.
4. Set concurrency and the gap between starts if required (defaults: 1 active download, 1-second start gap).
5. Click **Download displayed files**. Keep the page open until it finishes. The results show saved files and failures. **Stop** cancels an active fetch or stops between files; an in-progress disk write finishes.

Only the displayed report rows are included, not other pages or a previously saved scan. Each retained filename is fetched once per batch with the chosen concurrency and global start gap. Explicit sign-in redirects and HTTP 401/403/429/503 stop the run. Other failed files, including unexpected HTML responses, are logged and the batch continues unless three consecutive jobs fail; HTML is not saved as a PDF/document. Requests time out after two minutes. An HTML response alone cannot distinguish a broken file from a login page returned without a sign-in redirect.

Without folder mapping, raw files are saved with original names in the chosen folder. The first eligible report record for each filename is kept; later records with the same filename (case-insensitive) are skipped before requesting any URL. Non-empty files already in the destination folder are skipped before downloading. The resume manifest and, if needed, recovery staging files are stored alongside the batch. No suffixes are added to document names. No content comparison is performed; same filename does not establish identical contents. If the first record fails, later duplicate records are still skipped.

The migration master CSV already includes source record IDs and filenames. Its 40 duplicate-filename groups cannot be joined reliably by filename alone. Duplicate source records must be reconciled separately in the CSV if needed; only one file per filename is downloaded. Ordinary unique filenames can be matched to the existing CSV directly. Windows-invalid filenames stop the batch before downloading rather than silently renaming them.

Source checks use a simulated report and folder API. Live APEX report parsing, authenticated file responses, and the browser's actual folder-write permission still require a small live batch check by the user. If the panel reports no recognized report, check that the two required columns are visible before diagnosing markup changes.

Run the offline checks with `node download-check.cjs`.

Live download protocol confirmed by user Network evidence: the report href alone returns Manage Documents HTML. The working click calls APEX application process DOWNLOAD_DOCUMENT with x01 set to the document ID; JSON returns a temporary Oracle government object-storage URL. v4.25 uses apex.server.process for that authenticated request, then fetches the returned HTTPS URL with credentials omitted and writes the blob to the chosen folder. Temporary URLs are not persisted or logged. The cross-origin storage fetch still requires the storage server to permit browser access; a network/CORS failure stops the batch with an explicit message. User confirmed the v4.25 download protocol works live; v4.27 duplicate skipping still needs user verification.

## Quick download from home cards (v4.28)

On the Resource Centre home page the toolkit panel has a **Download** tab. Choose a folder (Chrome or Edge), click **Choose Documents**, untick anything you do not want, then **Download Selected**. Only cards currently shown on the page are offered; External Link cards have no file and never appear. The quick-download folder is remembered separately from the Manage Documents folder, so a quick save cannot change where a batch goes.

The card links carry only a document ID (a plain fetch of them returns a web page), so the tab uses the same APEX DOWNLOAD_DOCUMENT process as Manage Documents. Cards show a Display Name, not the original file name, so the original name is read from the storage response Content-Disposition header (live-confirmed 10/10/2026), falling back to the storage object name with its leading document-ID prefix removed. Because that name is only known after the response headers arrive, duplicate-name and existing-file skips happen then, before the file body is read. The first card for a name is kept; later same-name cards are skipped. Nothing is overwritten and no subfolders or suffixes are created. The stop rules, pause, timeout and HTML guard match Manage Documents.

Run the offline checks with `node download-cards-check.cjs`. Live use on the home page (process call from cards, folder picker, real downloads) still needs a small live check by the user.
